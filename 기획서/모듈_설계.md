> 기획서(`W02_기획서_초안.md`)의 범용 프로그램을 **어떤 조각으로 나눠 어떤 순서로 만드는지** 정리한 문서입니다.
> 상태 표시: ✅ 완료 / 🔄 진행 / ⬜ 아직 / 📝 설계만(실제 작동 아님)

## 1. 한눈에 보기


## 3. 만드는 순서와 이유

1. **M0·M1 (지금)** — 모든 모듈이 기대는 바닥이라 가장 먼저.
2. **M2 원본 읽기** — 데이터가 있어야 계산이 가능.
3. **M3 지표 → M4 규칙집** — 서로 독립이라 함께 가능. 판단의 재료.
4. **M5 엔진 핵심** — M2~M4를 엮어 "안건 → 평가 → 승인 → 작업" 흐름을 완성.
5. **M8 W02 → M9 화면** — 첫 예제가 끝까지 돌아가는지 확인. **여기서 정상 시연 가능.**
6. **M6 현금 재전망 → M7 AI** — 확장(현금 하회 구간)과 AI 역할 추가.
7. **M10 시연 도구** — 변경·정보 부족/거절 시연을 반복 재생.
8. **M11** — 여유가 있을 때만.

**중간 배포 지점(권장):** M0 직후(DB 켜기 확인), M9 직후(화면까지), M10 직후(최종 점검).

## 4. 모듈 사이 약속 (이걸 지키면 따로 만들어도 맞물립니다)

- **업무 모듈은 엔진을 호출하고, 엔진은 업무 모듈을 모릅니다.** (엔진에 "혜인" 같은 말이 들어가면 안 됨)
- **규칙은 코드가 아니라 데이터**로 둡니다. 승인권한 표를 고쳐도 판단 로직은 그대로.
- **원본과 가정을 섞지 않습니다.** 모든 안건·작업·가정 행에 `data_origin`(원본 / 가정 / 합성 / 가상입력)을 붙입니다.
- **이력은 추가만 합니다.** 지우거나 고치지 않습니다 (`case_events`).
- **AI는 정리와 설명만, 숫자 계산은 코드가** 합니다. 최종 결정은 사람.
- **DB 접근은 서버 코드에서만** (`"use client"` 파일 금지) — 템플릿 규칙.

## 5. DB 기본 구조 (M0)

| 테이블 | 담는 것 | 핵심 칸 |
|---|---|---|
| `decision_cases` | 결정해야 할 일(안건) | 업무 유형, 상태, **마감일**, 연결 대상 번호, 승인권자, 데이터 성격 |
| `case_events` | 이력 (추가만) | 안건, 사건 종류, 주체(시스템/AI/사람), 근거·이전/이후 상태 |
| `approvals` | 승인 요청과 결과 | 안건, 필요한 승인권자, 상태, 결정자, 결정 시각 |
| `tasks` | 후속 작업, 정보 부족 때의 확인 요청 | 안건, 종류, 담당 역할, 상태, 회신(가상 입력 가능) |
| `assumptions` | 계산에 쓰는 가정값, 모의 입력 | 이름, 값, 종류(가정/합성/가상입력), 적용 시점 |
| `source_rows` | 원본 CSV 한 줄의 복사본 | **원본 파일 경로, 행 번호**, 내용(JSON) |

- 테이블은 **필요할 때 이 파일에 추가**합니다 (`CREATE TABLE IF NOT EXISTS`). 구조를 바꿀 때 로컬은 `npm run db:reset`, 배포본은 `ALTER TABLE … ADD COLUMN IF NOT EXISTS`로 데이터를 보존합니다.
- `source_rows`는 CSV 전부를 한 테이블에 JSON으로 담는 방식입니다. 장점은 모든 파일을 같은 코드로 적재하고 출처를 보존하기 쉬운 것, 단점은 계산할 때 타입 변환이 필요한 것입니다. 느려지면 자주 쓰는 파일만 전용 테이블로 옮깁니다. **[가정: 사용자가 원본 읽기 방식 ②(DB 복사)에 동의한 것으로 보고 진행. 바꾸고 싶으면 알려주세요.]**

## 6. 이 설계에서 아직 정하지 않은 것

- AI 도우미가 쓸 모델·호출 방식 (M7 착수 전에 정함)
- 화면 구성의 세부 (M9 착수 전에 정함)
- 시연 데이터의 구체 값 (M10 착수 전에 정함)
