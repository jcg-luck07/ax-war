# 모듈 설계서 (v3 — 실사용 기준)

> 이 프로그램은 과제용 시연 도구가 아니라 **회사에서 쓰는 의사결정 프로그램**으로 만든다. 로그인한 사용자가 자기 역할로 안건을 접수하고, 승인하고, 회신하고, 작업을 처리한다.
> 상태: ✅ 실제 작동(시험 통과)

## 1. 구조

```
 화면 (app/)  할 일 · 안건 · 업무 흐름(BPMN) · 안건 접수 · 인플루언서 성과 · 현금 재전망 · 데이터 모델 · 사용자·권한
     │ 서버 동작 (app/actions.ts) — 로그인 사용자의 역할로 할 수 있는 일만 처리
 ┌───┴─────────────────────────────────────────────────────────────┐
 │ 업무 모듈  lib/modules/w02 (전속계약·확대 기안), w01 (재고 발주)  │ ← 업무마다 갈아 끼움
 └───┬──────────┬──────────────┬──────────────┬────────────────────┘
 ┌───┴────┐ ┌───┴──────┐ ┌─────┴──────┐ ┌─────┴───────┐
 │ 규칙집  │ │ 시맨틱 레이어 │ │ 업무 흐름   │ │ 사용자·권한   │
 │lib/rules│ │lib/semantic │ │lib/process │ │lib/app/auth  │
 └───┬────┘ └───┬──────┘ └─────┬──────┘ └─────┬───────┘
     └──────────┴────┬─────────┴──────────────┘
              ┌───────┴───────┐
              │ 공통 엔진       │  안건 → 평가 → 승인 → 작업 → 이력 → 재평가

              └───────┬───────┘
              ┌───────┴───────┐
              │ DB (PostgreSQL) │  원본 CSV 복사본(source_rows) + 안건·승인·작업·이력·사용자
              └───────────────┘
```

## 2. 시맨틱 레이어 (`lib/semantic/`)

화면과 판단이 CSV 를 직접 읽지 않고 **업무 대상·관계·측정값·지표를 선언한 모델**을 거쳐 읽는다 (dbt·Cube 같은 시맨틱 레이어 방식).

| 개념 | 뜻 | 이 프로젝트의 예 |
|---|---|---|
| 엔티티 | 업무 대상. CSV 한 파일 = 한 엔티티, 열마다 타입·뜻·주의 | 주문, 반품, 광고비, 캠페인, 인플루언서, 매출채권, 매입채무, 발주 … 14개 |
| 관계 | "이 행은 저 행 하나에 속한다" | 주문 → 캠페인 → 인플루언서, 주문 → SKU×채널 원가 |
| 집계 엔티티 | 집계 단위를 맞추려고 묶은 엔티티 | 주문별 환불 합계 |
| 측정값 | 한 엔티티를 기준으로 하는 합계·건수 | GMV, 환불, 제품원가, 광고비, 예상 회수액, 운영 지급액, 발주 대금 |
| 지표 | 측정값을 식으로 조합 | Net Revenue, **실질 공헌이익**, 명목·실질 ROAS, 반품률 |
| 차원 | 무엇별로 볼까 | 인플루언서별, 캠페인별, **현금 유출입 예정일(엔티티마다 날짜 열이 다른 시간 차원)** |
| 파라미터 | 원본에 없어 가정한 값 | 주문당 원가·배송비 적용 횟수, 환불 시 원가 회수 여부 |

- **컴파일러**(`compile.ts`): 질의를 SQL 로 번역한다. 기준 엔티티가 다른 측정값은 따로 집계한 뒤 차원 키로 합쳐서 **행이 부풀지 않는다**(fan-out 방지). 식에 쓰이는 값은 모두 바인딩 파라미터.
- **검증:** 같은 계산을 따로 손으로 짠 기준 구현(`scripts/reference/performance.ts`)과 대조해 4가지 가정에서 인플루언서 10명·캠페인 25개의 모든 값이 일치한다(`scripts/test-semantic.mjs`).
- **화면:** `데이터 모델` 메뉴에서 모든 정의·관계·가정·출처를 볼 수 있다.

## 3. 업무 흐름 (BPMN 방식, `lib/process/`)

- **선언**(`definitions.ts`): 레인(부서·역할), 노드(할 일·분기·시작/끝), 화살표. 전속계약·확대 기안·재고 발주 3개.
- **상태**(`state.ts`): 안건의 실제 승인·작업·이력에서 "끝남 / 지금 여기 / 앞 단계 대기 / 해당 없음"을 계산해 흐름 위에 얹는다.
- **그림**(`components/FlowDiagram.tsx`): 안건 화면에는 그 안건의 진행 상황을, `업무 흐름` 화면에는 단계마다 기다리는 안건 수를 보여 준다. "지금 · 재무 — 확인 요청 회신 → 다음 · 승인권자(결정)" 한 줄 요약도 같이 나온다.
- **정합성 시험:** 업무 모듈이 만드는 모든 후속 작업이 그림에 노드로 있고, 그림의 작업 노드는 실제로 만들어지는지 자동 확인한다(`scripts/test-app.mjs`).
- BPMN(`W02.bpmn`, 교육용 현재 업무)의 후속 작업 뼈대를 따르되, 시스템 판정·확인 요청·재평가 단계를 더해 다시 그렸다.

## 4. 사용자·권한 (`lib/app/auth.ts`)

- 배포본: axhub 로그인 사용자의 이메일로 역할을 찾는다. 이메일↔역할은 관리자가 `사용자·권한` 화면에서 등록한다. 로그인하지 않으면 볼 수만 있다.
- 승인: 요구 권한 이상인 역할만 결정할 수 있다 (재무·계약 담당은 승인 권한 없음, 관리자라도 승인 권한이 생기지 않음). 서버가 다시 확인하고, 엔진도 한 번 더 막는다.
- 회신·작업: 담당 부서 역할만 처리한다 (관리자는 모두).
- 로컬 개발: `.env.local` 의 `DEV_USER_*` 로 사용자를 정한다. 화면에 역할 전환 기능은 없다.

## 6. 약속 (코드로 지켜지는 것)

- 엔진은 업무를 모른다 (엔진 코드에 업무 이름이 없음을 시험으로 확인).
- 규칙·지표·흐름은 코드가 아니라 **선언(데이터)**. 바꾸면 모든 화면에 반영된다.
- 권한을 넘는 결정은 거부하고, 모르는 사실은 확정하지 않고 확인 요청으로 만든다.
- 원본과 가정을 섞지 않는다 (`data_origin`: 원본 / 가정 / 합성 / 가상입력 / 사용자입력).
- 이력은 추가만 한다.
- 계산·판정·요약은 모두 코드가 한다. **AI·LLM 은 쓰지 않는다.**
- 시연·초기화·가짜 회신 같은 과제용 기능은 화면에 없다.

## 7. 한계와 아직 안 한 것

- **배포본 DB 에는 원본 데이터가 없다.** 배포하려면 `axhub.yaml` 의 DB 를 켜고, 필요한 CSV(02_masil 2.1MB)를 저장소에 복사본으로 넣어 적재하는 방법을 정해야 한다.
- 현금 재전망은 이미 확정된 스케줄만 합산한다. 공식 전망과 40~50억 원 차이가 나는 원인은 확정하지 못했다.
- W01 은 '발주 승인 권한' 한 가지만 구현했다. Corevia 쪽 업무(W03~W08)는 구현하지 않았다.
- 계약 원문이 없어 성과 피 정산 조건·고정 피 지급 일정은 확인되지 않는다 (입력 또는 확인 요청으로 처리).
- 배포(axhub)는 하지 않았다.
